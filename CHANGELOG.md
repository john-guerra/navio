# Changelog

Every published version, newest first. The section for the version in
`package.json` becomes the body of its GitHub release, so it is written for
someone deciding whether to upgrade rather than as a commit list. A unit test
fails if the current version has no section here, and headings inside a version
use `###` - a `##` would start a new version section.

## 0.3.1

Everything below is new since 0.3.0, which shipped only the `height`/header-band
change and the `settingsKey` fix.

### Categorical colour

`defaultColorCategorical` was `d3.schemeCategory10`. Ten colours, and
`d3.scaleOrdinal` recycles its range, so an eleventh category was drawn in
exactly the colour of the first and nothing said so.

The default is now a generated 50-colour palette. It is computed, not
hand-picked: greedy farthest-point over a sampled HCL gamut, **scored on the
worst of normal, protan, deutan and tritan vision** rather than on normal
vision, and searched only over colours people can name (Heer & Stone's C3
model). It opens on colours close to `schemeCategory10`'s, so a small column
still looks ordinary.

Measured, minimum pairwise CIEDE2000 across all four vision types at 25
categories — 2.3 is the just-noticeable difference:

| palette | worst ΔE00 | unnameable |
|---|---|---|
| **nameable** (new default) | **5.7** | 0 |
| category10 (old default) | 1.6 | 1 |
| mokole 50 | 0.9 | 3 |
| turbo | 1.2 | 1 |
| rainbow at i/n | 0.4 | 4 |

`maxNumDistinctForCategorical` goes 10 → 30: the old value was the length of
`schemeCategory10` rather than a judgement about data, so a 12-category column
fell back to being treated as text.

`navio.palettes` exposes all of them, and a palette can be a function of the
category count. `nv.defaultColorCategorical = navio.palettes.category10`
restores the old look exactly, recycling included. Recycling now warns once per
column instead of being silent.

The [palettes example](https://john-guerra.github.io/navio/examples/palettes/)
scores every built-in and shows each through simulated colour-vision
deficiency; the numbers are generated by the same script that generates the
palettes, so the table cannot drift from the library.

Written up in `docs/ai/COLOR-CATEGORICAL.md`.

### Dark mode

```javascript
const nv = navio(d3.select("#nv"), { height: 400, theme: "dark" });
```

`theme` defaults to `"auto"`, which reads the background **behind the widget**
and re-reads it on every redraw — so a widget in a dark panel on a light page
comes out dark, which `prefers-color-scheme` could never have told it. There is
a **Theme** control in the settings panel too, under Layout, remembered with the
rest of the panel's settings. The data colours never change with the theme.

Settings stored by 0.2.x that spell out the old row-divider and tooltip colours
are migrated rather than honoured, since those were defaults and not choices.

### Fixes

- **#105** Row strokes are snapped to the device pixel grid. At dpr=1 a
  25-category column was rendering 87 distinct colours from 25.
- **#92** A plain click on a header now sorts reliably. The hit strips were a
  bandwidth wide with `paddingInner` gaps between them, so a press on a label
  and a release 3px away had the `<svg>` as their common ancestor and sorted
  nothing. It had been intermittent since 0.2.3.
- A hovered header grows only as far as it can be seen. It was cutting 259px
  off a long name — the growth destroyed what it existed to show.
- `nv.defaultColorCategorical` set after `addAllAttribs()` silently did nothing
  unless the palette was a function.
- A caller-supplied categorical scale keeps its explicit domain instead of
  having it reassigned in first-appearance order.
- `null`, `undefined`, `""` and `"none"` no longer enter a categorical domain;
  each one present consumed a colour that could never be drawn and shifted
  every category after it.
- `sortBy(name)` sorts by the registered attribute rather than the string.
- The header band is measured against the layout it is for, not the previous
  one — it was trailing a full redraw.
- Filter chips no longer float up to 140px into the data when the header band
  spills.
- The settings panel's Top offset slider redraws, and its colour swatches
  report the colour actually in use rather than `#000000`.
- A host page's own `button`, `select` and `input` rules no longer resize the
  settings panel. `button { margin: 0 6px 12px 0 }` - an ordinary rule for a
  page with buttons of its own - added 11px to every row of the attribute list.

### Docs

## 0.3.0

**`height` is now the RECORD extent, not the widget's total size.** The header
band is added on top of it rather than carved out of it, so the data area is
`height` however long the attribute names are. Before, a 180px widget with the
default `y0: 100` drew 40px of rows, and `y0: 140` drew none at all. Widgets get
roughly the old `y0` taller; set `height` down by that much to keep the previous
footprint.

The band is measured from the labels actually drawn (`autoHeaderSpace`, on by
default), so short names stop paying for headroom they never use and long ones
stop being cut off. Past `headerMaxSpace` (140px) the extra hangs above the
widget rather than growing it.

**A container with no `id` no longer remembers its settings.** The key used to
fall back to a per-page construction counter, which is not an identity: build
two Navios in a different order on the next load and each restored the other's
hidden columns and attribute types. Give the container a stable `id`, or set
`settingsKey`. `settingsKey` passed in the options object also works now - it
was being rejected as an unknown option (#99).

Also:

- The settings panel is no longer clipped by a host container that scrolls or
  hides its overflow (#100).
- Navio stops overwriting the host page's classes on its container (#101).
- `navio.describe()` and `docs/ai/API.md` describe all 51 options and the
  public methods, generated from one table in `src/params.js`.
